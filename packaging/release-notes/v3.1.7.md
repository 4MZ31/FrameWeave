## What's new in 3.1.7: crash safety

**PushFlow can't crash PushFPS anymore.** A crash report from an RTX 5090 showed PushFPS stopping inside ONNX Runtime (the engine PushFlow runs on) while PushFlow was shutting down a model, on every connect. Two safeguards are in now:
- Every ONNX Runtime call PushFlow makes is guarded. If one fails that badly, PushFlow switches itself off for the session and logs it, and PushFPS keeps running.
- If PushFPS still stops while PushFlow is starting, the next start notices and switches to another frame generation method (or turns frame generation off), with a message, so you're never stuck in a crash loop. You can pick PushFlow again at any time.

**Optimise for my PC puts your settings back after a crash.** If PushFPS stopped while *Optimise for my PC* was testing, your settings stayed on the combination that was being tested, and that could crash again on every connect. Your settings from before the run are now kept while it runs and restored automatically at the next start.

**How it was tested.** In CI on Windows without a graphics card: the build, the unit tests, PushFlow on WARP (Windows' software renderer, including the crash marker clearing after a normal close), the QML tests and the install test. The guarded failure paths themselves were not triggered in CI: no real crash could be reproduced there.

**Windows Defender note.** Defender may flag new PushFPS downloads as `Trojan:Win32/Tecabans.STV!cl`. This is a false positive from its cloud check on new, unsigned files, and it has been reported to Microsoft. Always check the zip against `SHA256SUMS.txt` on this page.
